# 推荐规则（recommendation-rules.md）

## 今日点餐输出规范

最多输出 3 个方案，不要一次输出大量菜单造成选择困难：

1. **最省钱方案** — 在满足基本一餐的前提下价格最低
2. **最符合个人习惯方案** — 与用户常点、喜好、门店习惯匹配度最高
3. **探索方案** — 与常点相近但最近较少尝试（基于当前 MCP 菜单，不是固定知识）

每个方案必须说明：

- 餐品明细（名称、规格）
- **🔥 方案总热量必须写在方案标题行**：如「最省钱 —— ¥26.9 🔥约 213 kcal（部分已知）」。热量是用户档案 track_calories=true 时的硬性字段，禁止只藏在表格里
- 预计价格（来源：calculate-price 或菜单标价，标明是否已含优惠）
- 可用优惠（券名、门槛，全部来自 MCP 实时数据）
- 逐项热量标注（已知/估算/未知，见下方营养库规则）
- 与用户偏好的匹配点
- 方案取舍（例如：为省钱放弃了饮料）
- 数据来源和不确定性（如"价格为到店自取价，外送另加配送费"）

## 营养库查询规则（省 token 缓存）

1. 工作台数据目录下 `nutrition-db.json` 缓存了 MCP `list-nutrition-foods` 全量营养数据（confidence=known）。推荐方案时**优先查本地营养库**，不要重复调用 list-nutrition-foods
2. 本地查不到的餐品（如新品）才调用 list-nutrition-foods 增量核对；确认仍无 → 热量标「未知（官方营养表未收录）」，严禁借用其他餐品数值编造
3. 套餐总热量 = 各项 kcal 相加；含未知项时写「约 XXX kcal + 未收录项」，不凑整成假精确

## 推荐前必须检查

按顺序核对，任何一条不满足则排除该方案：

1. **门店与就餐方式**：当前门店 + 用户选择的就餐方式（到店自取/麦乐送/得来速），菜单按对应 orderType/beType 查询
2. **临时规则**：temporary-rules.json 中未过期的规则（如"两周内不推荐薯条"）必须执行；每次推荐前用当前时间核对 expires_at
3. **忌口与排除项**：profile.json 的 avoid_items / dietary_restrictions 直接排除
4. **预算**：工作日午餐 / 晚餐预算分别适用；超预算方案需明确标出超出金额
5. **重复度**：与最近订单高度重复的方案降低优先级（用于探索方案）

## 优惠优化规则

用户问"怎么点最划算 / 这张券值得用吗"时：

- 比较：原始点法价格 vs 用券后价格 vs 套餐替换后价格
- 计算：实际节省金额 = 原价 − 实付
- 指出：是否需要额外购买用户不想要的餐品才能用券（这种情况明确说明"为用券多花了 X 元买你不要的东西"）
- 所有券名、门槛、有效期、价格必须来自实时 MCP（query-store-coupons / query-my-coupons / calculate-price），不编造
- 判断标准加入用户偏好：如果省钱方案包含用户忌口或明显不喜欢的餐品，宁可推荐贵一点但合适的方案，并说明取舍

## 我的常点分析

基于 orders.csv 统计：

- 最常点餐品、最常出现组合、最常门店、最常用优惠
- 最近重复过多的餐品（连续/高频出现时主动提示"最近常点 X，要不要换换？"）
- "与常点偏好相近但尚未尝试的餐品"：先从历史订单提取偏好特征（口味类别、价位、套餐结构），再对照**当前 MCP 菜单**找相似新品——不能只靠训练知识推荐可能已下架的餐品

## 热量与营养表述规范

- 只使用"已知热量""估算热量""记录热量"等观察性表述
- 禁止输出：医疗诊断、减肥保证、疾病相关建议、"这样吃一定会变胖"等绝对结论
- 热量数据仅用于：消费记录、趋势观察、点餐参考
- 用户开启 track_calories 后，每个方案附热量；未开启则默认不展示，用户问再给

## 临时规则生命周期

1. 用户说"接下来两周不要推荐薯条" → 写入 temporary-rules.json，记录 created_at / effective_at / expires_at（"两周"从当天算起）
2. 每次推荐、优惠优化前检查规则是否过期
3. 过期后停止影响推荐，可在用户查看档案时提示"X 条临时规则已过期，要清理吗？"
4. 用户可随时提前删除规则

## 多人点餐（第二阶段）

- 创建临时点餐任务：参与人数、总预算、每人口味与忌口
- 汇总需求，发现冲突（如两人忌口互斥、预算超支）时明确指出
- 生成整体方案 + 每人餐品清单
- 不假设 MCP 支持多人分账：只展示每人参考金额（均摊或按餐品计算，说明算法）
- 整体下单仍走高风险确认流程
